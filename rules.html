Linkumori can take rules from several places at once. Before any request is cleaned, it picks the sources to use, merges them, puts your custom rules on top, and removes what you switched off. This page walks through each step, with every case.

The pipeline

Rules are loaded at startup and again whenever you save custom rules or refresh remote rules in settings. Each load runs these steps, in order, and the engine then uses the result for every request until the next load.

  1. 1Pick the sourcesBuilt-in, remote, the verified cache, or none
  2. 2MergeRemote files with each other; with built-in in overload mode; then remote patches
  3. 3Custom rules on topA matching custom provider replaces; others are added
  4. 4Switch things offExcluded providers go; switched-off rules are skipped
  5. 5Clean requestsProviders run in order, pass after pass

Where rules come from

Built-in

Built-in rules

Ship with each release of the extension. On by default. Switch them off in settings to run only remote or custom rules.

Remote

Remote rule files

Off by default. Each is a pair of addresses: the rule file and a hash file. Linkumori fetches both, and loads the file only if its SHA-256 matches the hash.

Cache

Verified cache

The last remote rules that passed verification. Used when every remote file fails to load, if the cache belongs to the files you have configured.

Custom

Custom rules

The providers you write in the custom rules editor. Always applied last, on top of whatever else loaded.

Safety net. If the built-in rules file can't be read, Linkumori uses the remote cache, then the last rule set that loaded, then a small fallback list, so cleaning never stops entirely.

How a remote file is checked

  1. Fetch the hash file. It must hold 32 to 128 hexadecimal characters.
  2. Fetch the rule file and compare its SHA-256 with the hash. A mismatch rejects the file.
  3. Parse it as a CLN rule file with a providers object.
  4. Merge the files that passed, in the order you listed them, and save them as the verified cache.

Both requests skip the browser cache, so a file and its hash always come from the same moment. Files are fetched in parallel, and one failing file doesn't stop the others.

    Overload mode: merging sources

    Without overload mode, remote rules replace the built-in ones. With it, both load and providers for the same site merge into one, so you can add to the built-in rules instead of copying them.

    Order and matching

    1. Remote files merge first, with each other, in the order you list them.
    2. Then with built-in: built-in providers first, remote providers after.
    3. Providers merge only if they match: the same domainPatterns (in any order) or the same urlPattern, and the same methods, resourceTypes, completeProvider and forceRedirection. Anything else stays a separate provider.
    4. Lists join in load order: rules, rawRules and referralMarketing, built-in entries first. Exact copies count once.
    5. The same text twice: the later definition, from remote, wins. Without its own order it keeps the earlier one's place and order.

    Remote rule patches

    A remote file can change single rules that are already loaded, from the built-in rules or another remote file, without shipping a copy of them. It lists the changes in a top-level patches array. Each patch names one rule and the rule that takes its place.

    JSON
    {
  "cln": "1.0",
  "patches": [
    { "target": "amazon::field-qid", "section": "rules",
      "replace": { "matchPattern": "qid", "requestTypes": ["main_frame"] } }
  ]
}
    KeyWhat it holds
    targetThe rule to replace, written like its on/off toggle key: provider::id, domainPattern:<pattern>::id or urlPattern:<regex>::id. The id can be the rule's id, an alias, or its generated id
    sectionThe list the rule is in: rules, referralMarketing, rawRules, exceptions, redirections or fieldRedirections
    replaceThe new rule, a plain entry or a rule object, as it would be written in that list
    descriptionA note for people reading the file
    • When they run. After remote files merge (and, in overload mode, merge with built-in), before custom rules. A custom provider still overrides a patched one.
    • Patch-only files. A file with only patches needs no providers. When every remote file is one, the patches apply to the built-in rules. Without overload mode, built-in rules aren't loaded next to remote files with providers, so patches then reach only those files' rules.
    • Finding the rule. Merging can rename providers, so the domainPattern: / urlPattern: form is the one that always matches.
    • Toggles stay. The replacement keeps the old rule's id unless it sets its own; then the old id becomes an alias. A rule you switched off stays off.
    • Same safety as the file. The file's defaults apply to its replacements. A patch for a redirect list waits until you accept redirect for that file.
    • Checked. An invalid patches array rejects the whole file. Remote Rules Health lists each patch as applied, unmatched or skipped.

    The full syntax is in Filter syntax → Rule patches.

    Custom rules: replace or add

    Custom rules go on top of whatever base rule set loaded. Unlike overload mode, they don't join lists. Each custom provider either replaces every base provider with the same pattern, or is added next to the others.

    Only the pattern decides: the same urlPattern, or the same domainPatterns in any order. A custom provider overrides a base provider even when its methods, resourceTypes, completeProvider or forceRedirection differ. (Overload mode is stricter: there, providers merge only when all of those match too.)

    Changed after 100.66.0 In Linkumori 100.66.0 and earlier, a custom provider replaced a base provider only when its methods, resourceTypes, completeProvider and forceRedirection matched too. If any differed, it was added next to the base provider and both ran.

    A custom provider with the same pattern replaces the whole provider. Its rules are not combined with the built-in or remote ones. To add one rule to a built-in provider, copy that provider into the editor and add your rule to the copy. Or use a different pattern, so yours is added alongside.

    Defaults when rules merge

    When files with different defaults merge, nothing has to be looked up later: each file's defaults are written into that file's own rules as it loads, before any merge. Every rule then carries its values with it, so one merged provider can hold rules with different defaults side by side.

    2. 2Write them into its rulesOnly keys a rule doesn't set; the block is then removed

    How it works

    • Written in before merging. Each source's defaults are chosen and written into its rules when the file loads: the built-in file, each remote file (and each cached one), and your custom rules. The merge then sees ordinary rules.
    • A rule's own value wins. A default only fills a key the rule leaves out, such as requestTypes or exceptions.
    • The same text in two files: the later definition wins whole, so the values its file wrote into it come along. Because the defaults are part of each rule by then, two entries with the same text but different file defaults are not exact copies.
    • Exceptions stay with their file. A default exceptions list goes into that file's rules only. Merging never pools one file's exceptions into another file's rules.
    • History API setting. A provider's own historyBypassProtection beats the file default. When providers merge, it is copied onto each of that provider's rules, since the merged provider can hold only one value.
    • Complete providers. For a provider with "completeProvider": true, a file's requestTypes default becomes its resourceTypes, and default exceptions join its own. That happens before merging, and resourceTypes is part of what makes providers match, so the block can end up as a separate provider.

    Automatic, or started by you

    Two different things get called merging defaults. Linkumori does one on its own every time rules load. The other only happens when you start it in the custom rules editor.

    Automatic

    Writing defaults into rules

    When: every time rules load: at startup, when you save custom rules, and when you refresh remote rules in settings.

    What happens: each source's defaults block is chosen, by the setting under Rule defaults, and written into that source's own rules. Then the rules merge: remote files with each other, with built-in in overload mode, and custom rules on top.

    What it never does: combine two defaults blocks. Each rule keeps its own file's values, as shown above.

    You start it

    Merge from sources

    When: only when you open Manage rule defaults in the custom rules editor and choose Merge from sources.

    What happens: the defaults blocks of the sources you tick (yours, built-in, each remote file, custom) combine into one block, shown as Merged defaults.

    What it never does: change anything by itself. Nothing is stored until you copy the merged block into one of your sets and save. The next load then writes it into rules automatically.

    What each rule carries into a merge

    Merging never looks back at the original files. Everything it needs later is written onto the rules first.

    Carried on the ruleWritten whenUsed for
    Its file's defaults: requestTypes, exceptions, preprocessors, active, description, historyBypassProtectionIts file loadsWhere and how the rule runs
    Its provider's historyBypassProtectionProviders mergeWhether the rule runs on History API changes
    The file it came fromProviders mergeRemote Rules Health naming the file whose definition won
    Whether it may redirectIts remote file loads, from the capabilities you accepted for that fileA file's rewriting raw rules can't send a URL to another site until you accept redirect for that file

    Order on load: a remote file's defaults are written in first, then its capabilities are applied, and only then does it merge. Before merging, a file without an accepted capability also loses the entries that need it: its redirect lists without redirect, and completeProvider without block. The file tags never leave the extension: the custom rules editor strips them when you export a rule.

    The custom rules editor shows the defaults each loaded source used. Its Merge from sources tool is separate: it combines several defaults blocks into one block you can save, and doesn't change how rules merge.

    What a remote file may do

    A remote file gets capabilities from what it contains. Removing, rewriting and excepting work as soon as it loads. Redirecting and blocking wait until you accept them for that file in Remote Rules Health.

    CapabilityThe file containsActive
    striprules, rawRules, referralMarketing or $removeparam entriesOn load
    rewriteAn entry with a replacePatternOn load
    exceptProvider exceptions or @@ entriesOn load
    redirectredirections, fieldRedirections or forceRedirectionAfter you accept
    blockA provider with "completeProvider": trueAfter you accept

    Built-in and custom rules hold every capability. A file that gains a capability in an update waits for acceptance again.

    At run time

    • Providers run in turn. For each request, every provider whose pattern matches is tried. The first that changes, redirects or blocks the URL ends the pass.
    • Passes repeat. A changed URL starts a new pass, up to 10 per request. Settings → Unbounded cleaning cycles removes the cap; use it only for rules you trust, since two rules that redirect to each other then loop until the browser stops them. Cleaning a copied link and the rule tester stop as soon as the URL comes back to one already seen.
    • Inside a provider, entries run in the exact order CLN 1.0 defines. See Processing order and the run-order calculator.
    • Nothing reloads on a timer. Rules load at startup, when you save custom rules, and when you refresh remote rules in settings.
