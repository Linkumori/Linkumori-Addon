Linkumori can take rules from several places at once. Before any request is cleaned, it picks the sources to use, merges them, puts your custom rules on top, and removes what you switched off. This page walks through each step, with every case.

The pipeline

Rules are loaded at startup and again whenever you save custom rules or refresh remote rules in settings. Each load runs these steps, in order, and the engine then uses the result for every request until the next load.

  1. 1Pick the sourcesBuilt-in, remote, the verified cache, or none
  2. 2MergeRemote files with each other; with built-in in overload mode
  3. 3Custom rules on topA matching custom provider replaces; others are added
  4. 4Switch things offExcluded providers go; switched-off rules are skipped
  5. 5Clean requestsProviders run in order, pass after pass

Where rules come from

Built-in

Built-in rules

Ship with each release of the extension. On by default. Switch them off in settings to run only remote or custom rules.

Remote

Remote rule files

Off by default. Each is a pair of addresses: the rule file and a hash file. Linkumori fetches both, and loads the file only if its SHA-256 matches the hash.

Cache

Verified cache

The last remote rules that passed verification. Used when every remote file fails to load, if the cache belongs to the files you have configured.

Custom

Custom rules

The providers you write in the custom rules editor. Always applied last, on top of whatever else loaded.

Safety net. If the built-in rules file can't be read, Linkumori uses the remote cache, then the last rule set that loaded, then a small fallback list, so cleaning never stops entirely.

How a remote file is checked

  1. Fetch the hash file. It must hold 32 to 128 hexadecimal characters.
  2. Fetch the rule file and compare its SHA-256 with the hash. A mismatch rejects the file.
  3. Parse it as a CLN rule file with a providers object.
  4. Merge the files that passed, in the order you listed them, and save them as the verified cache.

Both requests skip the browser cache, so a file and its hash always come from the same moment. Files are fetched in parallel, and one failing file doesn't stop the others.

    Overload mode: merging sources

    Without overload mode, remote rules replace the built-in ones. With it, both load and providers for the same site merge into one, so you can add to the built-in rules instead of copying them.

    Order and matching

    1. Remote files merge first, with each other, in the order you list them.
    2. Then with built-in: built-in providers first, remote providers after.
    3. Providers merge only if they match: the same domainPatterns (in any order) or the same urlPattern, and the same methods, resourceTypes, completeProvider and forceRedirection. Anything else stays a separate provider.
    4. Lists join in load order: rules, rawRules and referralMarketing, built-in entries first. Exact copies count once.
    5. The same text twice: the later definition, from remote, wins. Without its own order it keeps the earlier one's place and order.

    Custom rules: replace or add

    Custom rules go on top of whatever base rule set loaded. Unlike overload mode, they don't join lists. Each custom provider either replaces a matching provider whole, or is added next to the others.

    A matching custom provider replaces the whole provider. Its rules are not combined with the built-in or remote ones. To add one rule to a built-in provider, copy that provider into the editor and add your rule to the copy. Or use a different pattern, so yours is added alongside.

    Your custom providerResult

    When both a base provider and a custom provider match a request, both still get to clean it. The first provider that changes, redirects or blocks the URL ends that pass, and the cleaned URL starts a new pass, so the other provider runs next.

    Switching rules off

    You can switch off a single rule, or a whole provider, without editing any file. Switched-off rules are left out when the providers are built.

    ScopeSaved asSwitches the rule off
    Providerprovider::idEverywhere in that provider
    PatterndomainPattern:||shop.example^::idOnly for URLs matching that one pattern
    • Toggles survive merges. If a merge replaces a rule, the replaced rule's id still switches the rule that runs.
    • Toggles survive edits. Switching off a rule without its own id pins its generated id, so the setting keeps working when the rule's text changes a little. A pin that no longer matches any rule shows as an orphaned toggle in the editor.
    • Renames. When a rule's id changes, its old ids in aliases keep saved toggles working.

    Rule defaults

    Each rule file can have a defaults block, for example request types or exceptions that every rule in the file gets unless it sets its own. In the custom rules editor, Manage rule defaults sets your own block and where it applies.

    A rule's own value always wins, and a provider's exceptions list is never changed by defaults. Defaults are applied to each file when it loads, so they stay with their file through overload mode.

    What a remote file may do

    A remote file gets capabilities from what it contains. Removing, rewriting and excepting work as soon as it loads. Redirecting and blocking wait until you accept them for that file in Remote Rules Health.

    CapabilityThe file containsActive
    striprules, rawRules, referralMarketing or $removeparam entriesOn load
    rewriteAn entry with a replacePatternOn load
    exceptProvider exceptions or @@ entriesOn load
    redirectredirections, fieldRedirections or forceRedirectionAfter you accept
    blockA provider with "completeProvider": trueAfter you accept

    Built-in and custom rules hold every capability. A file that gains a capability in an update waits for acceptance again.

    At run time

    • Providers run in turn. For each request, every provider whose pattern matches is tried. The first that changes, redirects or blocks the URL ends the pass.
    • Passes repeat. A changed URL starts a new pass, up to 10 per request. Settings → Unbounded cleaning cycles removes the cap; use it only for rules you trust, since two rules that redirect to each other then loop.
    • Inside a provider, entries run in the exact order CLN 1.0 defines. See Processing order and the run-order calculator.
    • Nothing reloads on a timer. Rules load at startup, when you save custom rules, and when you refresh remote rules in settings.
