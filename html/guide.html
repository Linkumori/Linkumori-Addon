Writing Linkumori rules

Linkumori cleans URLs with rules written in CLN Format 1.0 (Clean Link Notation), a JSON format. This guide goes from a first rule to every option, with examples you can copy.

The built-in rules, remote rule lists and your custom rules all use the same format. You write custom rules in the custom rules editor, which checks them when you save or import. An official ClearURLs rule catalog (data.min.json) is already a valid CLN file and can be used as it is.

1. The rules file

A rules file is one JSON object. Its providers object maps a name of your choice to a provider:

{
  "cln": "1.0",
  "providers": {
    "example": {
      "domainPatterns": ["||example.com^"],
      "rules": ["utm_source", "utm_medium"]
    }
  }
}

A provider says which URLs it handles and what to do with them. This one removes utm_source and utm_medium from every URL on example.com and its subdomains:

https://www.example.com/page?utm_source=news&utm_medium=mail&id=10
→ https://www.example.com/page?id=10

The provider name is only a label. Which URLs a provider handles is decided by domainPatterns or urlPattern.

Top-level keyWhat it does
providersRequired. The providers, by name.
clnOptional format version. The only valid value is "1.0". A file without it is read as 1.0 too; any other value rejects the file. It is not called version because the ClearURLs new rule format already uses that key.
metadataOptional information about the file.
defaultsValues for every rule of the file that doesn't set its own (chapter 12).
patchesRemote rule lists only: replacements for rules that are already loaded (chapter 15).

FieldWhat it does
domainPatternsWhich URLs the provider handles, as one domain pattern or a list of them (chapter 3). Use this or urlPattern, never both.
urlPatternWhich URLs the provider handles, as one regular expression matched against the full URL. Case is ignored.
indexPatternOnly with urlPattern: host hints such as ||example.com^, so the provider is only checked for those hosts instead of against every URL. It is a lookup hint, not a match condition.
rulesParameters to remove (chapters 4 and 5).
referralMarketingReferral and affiliate parameters to remove. Skipped while Allow referral marketing is on (chapter 10).
rawRulesRegular expressions run on the full URL; every match is deleted (chapter 6).
exceptionsURLs the provider leaves completely alone (chapter 7).
redirectionsSend the request to another address instead of editing it (chapter 8).
fieldRedirectionsSend the request to the value of a parameter (chapter 8).
completeProvidertrue blocks every request the provider matches, while Allow domain blocking is on.
forceRedirectiontrue: when a page load (main_frame) is redirected, the whole tab navigates to the new address, not just the network request.
methodsOnly handle these HTTP methods, for example ["GET"]. Left out: every method.
resourceTypesOnly handle these request types, for example ["main_frame", "xmlhttprequest"]. Left out: every request type.
historyBypassProtectionDefault true. false skips the whole provider when a page changes its own address with the History API (pushState/replaceState). Normal network requests are still cleaned.
activefalse switches the provider off without deleting it.

3. Which URLs a provider handles

domainPatterns is a list of domain patterns. A URL matches if any of them matches. The same patterns are used in front of exceptions, redirections, $removeparam filters and raw rules.

"domainPatterns": ["||example.com^", "||example.*^", "||shop.example.org^/cart"]
PatternMatches
||example.com^example.com and every subdomain
||example.*^example on any public suffix (example.de, example.co.uk, …)
||example.com^/paththat host and its subdomains, when the path starts with /path
||*.example.com^the same as ||example.com^
|https://example.com/URLs that start with exactly this text
…/page.html|URLs that end with exactly this text
/regex/ithe full URL, as a regular expression
example.com/pathURLs that contain this text anywhere (no leading |)
*every URL

^ marks the end of the host name, or a separator such as /, ?, : or the end of the URL. * is a wildcard.

|| stands for a domain: the host and every subdomain. A single | stands for the very start of the URL and must be followed by a scheme such as https://. For a domain you always want ||; |example.com^ can never match, so the editor rejects it.

For example, ||smile.amazon.*^ reads as: || the host and its subdomains, smile.amazon the required labels, .* any public suffix (.com, .co.jp, .de, …), and ^ the end of the host.

To match with a regular expression instead, use urlPattern, and add indexPattern so the provider is only checked on those hosts:

"news": {
  "urlPattern": "^https?:\\/\\/(?:[a-z0-9-]+\\.)*?news\\.example\\.com\\/article",
  "indexPattern": ["||news.example.com^"],
  "rules": ["share_id"]
}

A provider has domainPatterns or urlPattern, never both. If you need both kinds of match, make two providers.

4. Removing parameters

Each entry in rules removes parameters from the query (?a=1) and from the fragment (#a=1). An entry is one of:

EntryExampleRemoves
a parameter name"utm_source"exactly that parameter
a name regex"utm_[a-z]+"every parameter whose whole name matches; case is ignored
a $removeparam filter"$removeparam=fbclid"see chapter 5

"fbclid" and "$removeparam=fbclid" remove the same thing. Use the plain name unless you need something from chapter 5. Any entry can also be written as a rule object (chapter 9).

Rules for part of a provider

A plain name applies to every URL the provider matches. To remove a parameter on only some of them, put a pattern in front of a $removeparam filter:

"amazon": {
  "domainPatterns": ["||amazon.*^"],
  "rules": [
    "qid",
    "||amazon.de^$removeparam=tag",
    "||smile.amazon.*^$removeparam=sr",
    "||amazon.*^/gp/$removeparam=ref_"
  ]
}

Here qid is removed on every Amazon site, tag only on amazon.de, sr only on smile.amazon, and ref_ only under /gp/. The pattern narrows the provider's own patterns; it can never widen them.

5. $removeparam filters

A $removeparam filter has this shape; the parts in brackets are optional:

[@@][pattern]$removeparam[=value][,modifier,modifier,…]
  • @@ turns the filter into an exception that keeps the parameter (see below).
  • pattern narrows the filter to some of the provider's URLs (chapter 3). Left out, it applies to every URL the provider matches.
  • =value picks the parameters. Left out, every parameter is removed.
  • Modifiers say when the filter fires. Every modifier listed must hold; there is no "or" between them.

The value

The first character of the value decides what it means:

FilterRemoves
$removeparamevery parameter
$removeparam=~refevery parameter except ref
$removeparam=/^utm_/iparameters whose name, or name=value together, matches the regular expression; add i to ignore case
$removeparam=|utm_parameters whose name starts with utm_
$removeparam=fbclidexactly that parameter; case is ignored unless you add match-case

Escaping a parameter name

A backslash makes the next character literal, so any parameter name can be targeted:

ValueRemoves the parameter named
\~foo~foo
\|foo|foo
\/foo//foo/
a\,ba,b (the comma doesn't start the modifiers)
\\foo\foo

These five are the only escapes in a name value; a backslash before any other character is an error. Inside a /regex/ value the backslash keeps its regex meaning. The escapes work in rules, referralMarketing, fieldRedirections and @@ entries. In JSON, write each backslash twice: "$removeparam=\\~foo".

Modifiers

Modifiers come after the value, separated by commas. Separate several values of one modifier with |, and put ~ in front of a value to exclude it:

"rules": [
  "||example.com^/search$removeparam=q,domain=example.com|~shop.example.com",
  "$removeparam=sid,third-party,method=get,~xmlhttprequest"
]
ModifierWhat it does
domain=a.com|~b.comonly when the page that made the request is (or, with ~, is not) one of these; regex values are allowed
to=a.com|~b.comonly when the request itself goes to one of these, whatever page made it
method=get|~postonly for these HTTP methods: get, head, options, post, put, patch, delete, connect
first-party, third-partyonly when the request goes to the same registrable domain as the page (a.example.com and b.example.com count as the same), or to a different one
strict-first-party, strict-third-partythe same, but comparing the exact host name, so a subdomain counts as third-party
document, subdocument, script, stylesheet, image, imageset, media, font, object, xmlhttprequest, websocket, ping, otheronly for these request types; ~type excludes one
match-caseparameter names are compared case-sensitively
history-bypass-protection=falseskip this filter when a page changes its own address with the History API. Also accepts true/false, 1/0, yes/no

The four *-party modifiers can't be combined with each other; first-party,third-party is rejected.

For example, ||example.com^$removeparam=sid,domain=~partner.com,method=get,third-party removes sid on example.com, only for GET requests made by a page on another site, and never when that page is partner.com.

Keeping a parameter with @@

A filter that starts with @@ keeps the parameter instead of removing it. Here ref is removed everywhere except on GitHub:

"rules": [
  "$removeparam=ref",
  "@@||github.com^$removeparam=ref"
]
  • An @@ entry only protects against $removeparam filters. A plain entry such as "ref" still removes the parameter; use a rule object's exceptions for that. Raw rules have their own @@…$rawrule= entries (chapter 6).
  • Where you list it doesn't matter, and it can't have an order.
  • Its pattern is checked against the URL as the provider received it, before raw rules run. An @@ entry scoped to a path that a raw rule deletes still matches.
  • It also covers other providers' filters for requests made by a page this provider matches, which is handy for carving one site out of a rule defined elsewhere.

6. Raw rules

A raw rule is a regular expression run on the full URL; every match is deleted. Use it for text that is not a name=value parameter, such as Amazon's /ref=… path segment:

"rawRules": ["\\/ref=[^/?]*"]

Raw rules run before rules, ignore case and replace every match (flags gi, or g with match-case). In JSON, write each backslash twice.

Only on some URLs

A raw rule can take the pattern and modifiers of a $removeparam filter, with rawrule= last. Everything after rawrule= is the regular expression:

"rawRules": [
  "||amazon.*^/dp/$rawrule=\\/ref=[^/?]*",
  "||example.com^$third-party,method=get,rawrule=\\/sid=[^/?]*"
]

The pattern and modifiers decide where the rule runs; the regular expression is still what gets deleted.

Stopping raw rules on some URLs

An entry that starts with @@ and ends in rawrule= keeps raw rules from running where its pattern matches:

"rawRules": [
  { "id": "ref-strip", "matchPattern": "\\/ref=[^/?]*" },
  { "matchPattern": "@@||smile.example.com^$rawrule=", "targetId": "ref-strip" },
  "@@||example.com^/checkout/$rawrule="
]
  • With nothing after rawrule=, it stops every raw rule of the provider on those URLs.
  • With a regular expression after rawrule=, it stops the raw rules with that regular expression.
  • As a rule object with targetId, it stops only the raw rule with that id or alias.

To skip the whole provider, use exceptions instead.

7. Exceptions

If a URL matches an entry in exceptions, none of the provider's rules run for that request. An entry is a regular expression against the full URL, or a domain pattern that starts with |:

"exceptions": [
  "^https?:\\/\\/mail\\.google\\.com\\/mail\\/u\\/",
  "||accounts.google.com^",
  "||example.com^/login"
]

Exceptions ignore case. To skip a single rule instead of the whole provider, give that rule its own exceptions (chapter 9).

8. Redirects

Redirect rules skip tracking pages by going straight to the real destination. They only run while Enable Third-Party Redirect Bypass is on.

Redirect to part of the URL

An entry in redirections is a regular expression with exactly one capture group, ( … ). The request goes to what the group captured, URL-decoded. Write any other group as (?: … ):

"redirections": [
  "^https?:\\/\\/(?:[a-z0-9-]+\\.)*?google(?:\\.[a-z]{2,}){1,}\\/url\\?.*?(?:url|q)=(https?[^&]+)"
]

Redirect to a fixed address

An entry that starts with | sends every matching URL to one address:

"redirections": ["||go.example.com^$redirect=https://example.com/"]

Redirect to a parameter's value

fieldRedirections names the parameter that holds the destination, so no regular expression is needed. It takes the same entries as rules:

"fieldRedirections": ["redirect", "continue_url", "$removeparam=/^(u|dest)$/i"]

Whichever matching parameter comes first in the URL wins. For https://site.example/away?redirect=https://real.example/page, the request goes to https://real.example/page.

Valid redirect targets

A redirect only happens to an absolute http or https address with a host. This is checked after preprocessors and percent-decoding. An invalid target makes the entry count as not matching: nothing is redirected, and the provider's later steps run on the unchanged URL.

TargetRedirects?
https://real.example/pageyes
https%3A%2F%2Freal.example%2Fpageyes, to https://real.example/page
javascript:alert(1), ftp://files.example/xno: the scheme is not http or https
//real.example/page, /local/page, real.example/pageno: not an absolute address

A raw rule whose result has a different scheme, host or port than its input counts as a redirect too, even when it only deletes text: deleting secure- from https://secure-bank.example/ lands on another site. It needs a valid target, and in a remote rule list the redirect approval (chapter 15). Otherwise the rule leaves the URL as it was.

9. Rule objects

Any entry, in any list, can be an object instead of a string. Use one when a rule needs a stable id, should start switched off, should rewrite instead of remove, or should only run in some cases:

"rules": [
  "utm_source",
  {
    "id": "session-token",
    "matchPattern": "token",
    "active": false,
    "requestTypes": ["main_frame"],
    "exceptions": ["^https:\\/\\/example\\.com\\/account"],
    "description": "Session token; off until switched on"
  }
]
KeyWhat it does
matchPatternRequired. The text you would write as a plain entry in that list.
idA stable name (letters, digits, -, _) used to switch the rule on and off (chapter 14).
aliasesThe rule's previous ids, so a setting saved under an old id keeps applying after a rename.
replacePatternRewrite instead of remove; §1§, §2§, … are the captured values.
preprocessorsTransform the captured values first.
requestTypesOnly for these request types, for example ["main_frame"]. Cleaning without a request (Copy clean link, the cleaning tool, History API changes) counts as main_frame.
exceptionsURLs (regular expressions) where this one rule does not run.
flagsRegular expression flags, as a string. Default i; in rawRules, gi (or g with match-case).
orderRun the rule earlier or later within its stage (chapter 13).
referralMarketingtrue: a rule in rules also counts as a referral-marketing rule (chapter 10).
historyBypassProtectionThe provider switch of the same name, for this one rule. It beats the provider's value and the file default.
activefalse: the rule starts switched off.
descriptionA note for people reading the file; it must be a string.
targetIdOnly on @@…$rawrule= entries: the id of the raw rule it stops.

Rewriting instead of removing

With replacePattern, a rule in rules keeps the parameter and replaces its value, which is §1§. In rawRules and redirections, §1§, §2§, … are the capture groups:

"rules": [
  { "id": "wrap-token", "matchPattern": "token", "replacePattern": "clean-§1§" }
],
"rawRules": [
  { "id": "ref-to-path", "matchPattern": "\\/ref=([^/?]*)", "replacePattern": "/r/§1§" }
]

Here ?token=abc123 becomes ?token=clean-abc123. A rewrite applies at most once per request, so it doesn't keep wrapping the value.

Preprocessors

Preprocessors change captured values, in order, before replacePattern or a redirect uses them. inputs is "all" or a list of group numbers:

"redirections": [
  {
    "id": "unwrap-base64",
    "matchPattern": "^https?:\\/\\/out\\.example\\.com\\/\\?u=([^&]+)",
    "preprocessors": [{ "type": "base64Decode", "inputs": [1] }],
    "replacePattern": "§1§"
  }
]

The types are urlEncode, urlDecode, doubleUrlEncode, doubleUrlDecode, base64Encode and base64Decode.

10. Referral marketing

referralMarketing takes the same entries as rules. They only run while Allow referral marketing is off, so affiliate links keep working if you turn it on:

"referralMarketing": ["tag", "$removeparam=/^aff_/"],
"rules": [
  { "matchPattern": "ref_id", "referralMarketing": true }
]

A rule can stay in rules and still count as referral marketing, with "referralMarketing": true. Don't put the same text in both rules and referralMarketing; the editor warns about it.

11. Methods and request types

These narrow down when a provider or a rule runs:

FieldWhat it does
methodsHTTP methods the provider handles
resourceTypesrequest types the provider handles
requestTypesrequest types one rule object handles (also settable in defaults)
method=…, document, xmlhttprequest, …the same for one $removeparam filter or raw rule
 
"example": {
  "domainPatterns": ["||example.com^"],
  "methods": ["GET", "POST"],
  "resourceTypes": ["main_frame", "sub_frame", "xmlhttprequest"],
  "rules": [
    { "matchPattern": "ref_src", "requestTypes": ["main_frame"] },
    "$removeparam=trk,xmlhttprequest,method=post"
  ]
}

Request types use the browser's names: main_frame (a page), sub_frame (a frame), xmlhttprequest, script, image and so on. Filter modifiers call the first two document and subdocument.

Request types come only from the rules: there is no request type list in Settings. With none of these set, a rule cleans every request type.

12. Defaults

A top-level defaults block gives every rule of the file values it doesn't set itself:

{
  "cln": "1.0",
  "defaults": {
    "requestTypes": ["main_frame"],
    "exceptions": ["^https:\\/\\/example\\.com\\/keep"]
  },
  "providers": { … }
}
KeyDefault for each rule's…
activeactive; false switches every rule off unless it says "active": true
descriptiondescription
requestTypesrequestTypes; "all" or leaving it out means every type
preprocessorspreprocessors
exceptionsexceptions
historyBypassProtectionhistoryBypassProtection
  • A rule's own value always wins, and a rule's exceptions replace the default list instead of adding to it.
  • Defaults apply to rules, rawRules, referralMarketing, redirections and fieldRedirections. A provider's own exceptions list is left alone. $redirect= entries only use active.
  • Each file keeps its own defaults: the built-in rules, each remote list and your custom rules, also when overload mode merges them.
  • For a completeProvider, the default requestTypes and exceptions also limit the block.
  • Unknown keys and wrong types are errors, and a remote list with an invalid defaults block is rejected.

Your own defaults

In the custom rules editor, Manage rule defaults opens a form where you set a defaults block of your own and choose where it replaces the files' own:

  • Each source's own (the default): every file uses its own defaults.
  • Yours for built-in and remote rules: built-in and remote rules use yours; custom rules keep their own.
  • Yours for all rules: every rule uses yours.

The same form can edit the defaults of the built-in rules and of each loaded remote list. Your edit is stored in the extension, not in the file, and Reset to the file's defaults drops it. Merge from sources… combines the defaults of the sources you tick; nothing is stored until you save.

13. How a URL is processed

For each provider that matches the URL and allows the request:

  1. exceptions: if one matches, the provider is skipped.
  2. redirections, then fieldRedirections: a match with a valid target redirects the request.
  3. completeProvider: the request is blocked.
  4. rawRules run on the full URL.
  5. rules and referralMarketing remove or rewrite parameters.
  6. $removeparam filters run, except where an @@ entry keeps the parameter.

The first provider that changes, redirects or blocks the URL wins. The new URL then goes through the same steps again (see When processing stops).

Run order and order

Steps 4 and 5 are sorted together, by these rules in turn:

  1. Raw rules always run first. No order moves a rules entry ahead of a raw rule. A cleanup that must happen before a raw rule has to be a raw rule itself.
  2. Inside a stage, rules with order run before rules without one, lowest first. Negative numbers and fractions are allowed. order: 10 doesn't mean "tenth": it means after the stage's ordered rules below 10 and before all its unordered rules.
  3. Then by list: rules, then rules objects marked "referralMarketing": true, then referralMarketing.
  4. Then by position in the list. Every entry keeps its place, including entries written like "3" or "20".

Here the token is rewritten before utm_source is removed, although it comes second:

"rules": [
  "utm_source",
  { "id": "token-rewrite", "matchPattern": "token", "replacePattern": "clean-§1§", "order": 1 }
]

Rules that are off are left out. $removeparam filters and @@ entries are outside this sort and can't have an order, not even null; filters always run last.

Same text twice

Two entries with the same matchPattern text in one group are one rule. The groups are raw (rawRules), field (rules without the referral mark) and referral (marked rules objects, then referralMarketing). This mostly happens when rule lists are merged.

  • The last definition that isn't off wins, with all its keys.
  • Without its own order, the winner takes the first definition's position and the nearest earlier order. "order": null means no order, and drops an inherited one.
  • The ids and aliases of replaced definitions switch the winner on and off too.
  • While referral-marketing rules run, a referral entry replaces a field entry with the same text.
  • A raw rule and a field rule with the same text don't collide; both run.

Inside one list, two different entries with the same text are an error, and an exact copy is a warning.

When processing stops

  • At most 10 cycles run per request; at the cap the URL is used as it stands.
  • A rule with replacePattern applies at most once per request.
  • A step that doesn't change the URL doesn't start a new cycle.

Settings → Unbounded cleaning cycles (off by default) removes the 10-cycle cap for rule chains that need more. Processing then ends when a cycle changes nothing, but two rules that redirect to each other loop until the browser gives up and the page doesn't load. Turn it on only for rules you trust.

14. Rule ids and on/off switches

Every rule has an id. A rule without id gets one from its list and its text: "utm_source" in rules becomes field-utm-source. A generated id changes when the rule's text changes, and a switched-off rule would then switch back on. Give a rule its own id when it must keep its on/off setting through edits, and list old ids in aliases when you rename it.

A rule is switched on and off by its provider and id together, such as shop::session-token, so two providers can use the same id. The custom rules editor may also save it under the provider's pattern, such as domainPattern:||shop.example^::session-token; both forms work.

  • Within one provider, every id and alias must be different. Generated ids count.
  • An id can't contain a colon.
  • A setting saved under a bare id, without its provider, switches nothing; switch the rule off again in the custom rules editor.

15. Remote rule lists

Remote rule lists are rule files Linkumori downloads, optionally checked against a hash file. A list with an invalid cln value, defaults block or patches array is not loaded, and Remote Rules Health reports it.

Redirect and block need your approval

What a remote list can do is worked out from its content when it loads:

CapabilityThe list has it when it containsActive on load
stripa rules, rawRules or referralMarketing entry, or a $removeparam filteryes
rewritean entry with a replacePatternyes
excepta provider exceptions entry or an @@ entryyes
redirecta redirections or fieldRedirections entry, or forceRedirectionafter approval
blocka provider with "completeProvider": trueafter approval

Approve redirect and block per list in Remote Rules Health. Until then, that list's redirects and blocks stay off, and its raw rules can't send a URL to another site; the rest of the list works right away. When an update adds a new capability, it waits for approval too. Built-in and custom rules have every capability.

Overload mode

Normally, remote lists that have providers replace the built-in rules; lists that hold only patches are applied to the built-in rules. With Enable Overload Mode on, they load together, using one of three strategies:

  • Patch mode only: apply the remote lists' patches to the built-in rules; remote providers are left out.
  • Patch mode + merge: merge built-in and remote providers, then apply patches.
  • No patch mode + merge: merge the providers and skip patches.

When merging, remote lists are merged with each other in the order you list them, then with the built-in rules (built-in first). Only providers with the same domainPatterns (or urlPattern) and the same methods, resourceTypes, completeProvider and forceRedirection merge; their rules, rawRules and referralMarketing are joined, and Same text twice decides which copy runs. Remote Rules Health lists every replaced rule as a notice.

Custom rules are applied last. A custom provider replaces every loaded provider with the same pattern; their rules are not combined.

Rule patches

A remote list can replace single rules that are already loaded, without publishing a full copy, in a top-level patches array:

{
  "cln": "1.0",
  "patches": [
    {
      "target": "amazon::field-qid",
      "section": "rules",
      "replace": { "matchPattern": "qid", "requestTypes": ["main_frame"] },
      "description": "Only strip qid on page loads"
    },
    {
      "target": "domainPattern:||amazon.*^::strip-ref",
      "section": "rawRules",
      "replace": "\\/ref=[^/?#]*"
    }
  ]
}
KeyWhat it does
targetRequired. The rule to replace, written like its on/off key: providerKey::id, domainPattern:<pattern>::id or urlPattern:<regex>::id.
sectionRequired. rules, referralMarketing, rawRules, exceptions, redirections or fieldRedirections.
replaceRequired. The new rule, as a plain entry or a rule object.
descriptionA note for people reading the file.
  • Patches run after remote lists are merged and before custom rules. A file with only patches needs no providers.
  • Merging can rename providers, so the domainPattern: or urlPattern: form is the one that always finds them.
  • The replacement keeps the old rule's id, or takes the old id as an alias, so on/off settings keep applying.
  • A patch for a redirect waits for the list's redirect approval. A patch whose target matches nothing changes nothing.
  • Remote Rules Health lists each patch as applied, unmatched or skipped.

16. Rules and the whitelist

The whitelist is separate from a provider's exceptions: it lists sites you told Linkumori to leave alone, with no rule file involved. Entries look like example.com, *.example.com (the site and its subdomains) or example.* (any suffix). Whitelisting a page also covers everything it loads.

17. Complete examples

Clean one shop

Removes tracking parameters and an affiliate id on one shop, and leaves its checkout pages alone:

{
  "cln": "1.0",
  "providers": {
    "shop": {
      "domainPatterns": ["||shop.example^"],
      "rules": ["utm_source", "utm_medium", "utm_campaign", "$removeparam=/^pk_/"],
      "referralMarketing": ["aff_id"],
      "exceptions": ["||shop.example^/checkout"]
    }
  }
}

Remove UTM parameters everywhere

The pattern * matches every URL:

{
  "cln": "1.0",
  "providers": {
    "everywhere": {
      "domainPatterns": ["*"],
      "rules": ["$removeparam=/^utm_/i"]
    }
  }
}

Skip a click tracker

Sends links through a click tracker straight to their destination, which is in the url parameter:

{
  "cln": "1.0",
  "providers": {
    "click-tracker": {
      "domainPatterns": ["||click.example.net^"],
      "fieldRedirections": ["url"]
    }
  }
}

Keep a parameter on one page

Removes ref everywhere on the site except on the login page, which needs it:

{
  "cln": "1.0",
  "providers": {
    "site": {
      "domainPatterns": ["||example.com^"],
      "rules": [
        "$removeparam=ref",
        "@@||example.com^/login$removeparam=ref"
      ]
    }
  }
}

18. Checking your rules

The custom rules editor checks rules when you save or import them, and node linkumori-cli-tool.js lint-rules <file> runs the same checks. Besides broken JSON and invalid regular expressions, they reject rules that would load but quietly do the wrong thing, such as:

  • domainPatterns and urlPattern on one provider
  • a pattern with a single | and no scheme, such as |example.com^
  • a regular-expression redirect without exactly one capture group
  • unknown fields, keys and modifiers
  • a cln value other than "1.0"
  • an id or alias used twice in one provider
  • two different entries with the same text in one list
  • an order on a $removeparam filter or @@ entry, null included
  • a $redirect= address that is not http or https
  • a backslash in a $removeparam name before a character that has no escape
  • an @@…$rawrule= entry that stops no raw rule

They also warn about exact copies, and about the same text in both rules and referralMarketing. If saving fails, the message names the provider, the list and the entry.
